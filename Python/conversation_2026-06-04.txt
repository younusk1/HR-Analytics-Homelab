DESIGN DECISIONS & REASONING
=============================

1. WHY ENVIRONMENT VARIABLES?
   - Credentials in code = security risk if repo is ever public
   - Environment variables allow different values per environment (dev/prod)
   - os.environ.setdefault() provides sensible defaults while allowing overrides
   - Can be overridden by actual env vars if needed in future

2. WHY STRUCTURED LOGGING?
   - print() output gets mixed with errors and is hard to parse
   - logging module provides timestamps, severity levels, and consistent formatting
   - Easier to debug issues when you have full context (file, line, timestamp)
   - Can be configured to log to file later if needed

3. WHY SEPARATE MODULES?
   - input_data.py = library of functions (reusable ETL logic)
   - process_all_tables.py = orchestration script (uses the library)
   - Follows separation of concerns principle
   - Allows future scripts (e.g., n8n workflow) to import and use process_csv()

4. WHY TIMESTAMP-VERSIONED OUTPUT FILES?
   - Each run creates a new file instead of overwriting
   - Easy to track processing history and audit trail
   - Can reprocess without losing previous results
   - Helpful for debugging if something goes wrong

5. WHY "APPEND" MODE BY DEFAULT?
   - if_exists="append" is safer for production (no data loss)
   - if_exists="replace" is commented as option for explicit use
   - Thinking: defaulting to the safest option prevents accidents
   - User can explicitly choose "replace" if they understand the consequences

6. WHY RETURN DICT INSTEAD OF RAISE?
   - Allows process_all_tables.py to collect all results
   - Individual table failures don't stop processing of other tables
   - Better UX for a summary report showing which tables succeeded/failed
   - Easier to handle in batch operations than exceptions

8. SQLALCHEMY 2.0+ COMPATIBILITY FIX
   - Error encountered: "Not an executable object: 'SELECT COUNT(*) FROM employees'"
   - Root cause: SQLAlchemy 2.0+ requires text() wrapper for raw SQL strings
   - Solution applied:
     * Added import: from sqlalchemy import text
     * Wrapped SQL queries: connection.execute(text(f"SELECT ..."))
     * Applied to both query_database.py and query_interactive.py
   
   THINKING:
   - SQLAlchemy 2.0 enforces stricter type checking for SQL execution
   - Using text() explicitly marks raw SQL strings for execution
   - This prevents accidental SQL injection and improves code clarity
   - Future-proofs scripts for newer SQLAlchemy versions
